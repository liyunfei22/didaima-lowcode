# 01 · 低代码平台全景调研

> 本文是低代码学习项目的调研交付物之一。目标：站在 2026 年的时点，把主流低代码平台按"路线"而非按"厂商"理清楚——**它们解决什么问题、架构怎么分、我们该抄什么**。
> 配套阅读：`02-core-principles.md`（核心原理详解）、`03-references.md`（资料清单）、`architecture.md`（我们自己的架构取舍）。

---

## 1. 一份全景地图：六大类低代码平台

低代码平台可以分成六大类，它们的差异其实不在"低代码"三个字上，而在**"产物是什么"**：

| 类别 | 代表产品 | 产物形态 | 目标用户 |
|---|---|---|---|
| ① 内部工具（Internal Tools） | Retool、Appsmith、Budibase、ToolJet | 内部管理台/运维台/CRUD 页面 | 会一点 JS 的开发者 |
| ② 企业级 aPaaS | Mendix、OutSystems、Power Apps | 复杂业务应用/核心系统 | 企业 IT 团队 + 公民开发者 |
| ③ 页面/应用搭建框架 | amis、lowcode-engine、tmagic-editor | 页面配置化渲染/可嵌入引擎 | 前端开发者 |
| ④ 表单流程 SaaS | 简道云、明道云、氚云、轻流 | 数据收集/审批流转应用 | 业务人员 |
| ⑤ 云厂商 PaaS | 宜搭、微搭、魔笔、爱速搭、CodeWave | 云上托管的应用平台 | 企业客户 |
| ⑥ 通用无代码/Nocode | Bubble、Webflow、Framer | 面向创业者的产品级网站/应用 | 非技术创业者 |

对学习来说，**最值得精读的是①②③三类**——它们才是"平台"（有自己的内核引擎），④⑤大多只是在 ①-③ 的引擎上做业务模型层；⑥偏设计自由度，架构价值反而不大。

---

## 2. 内部工具类：Retool / Appsmith（我们的直接对标）

内部工具是低代码最主流的场景：**表单 + 表格 + 按钮 + 数据源** 的管理页面。我们的平台定位就是这一类。

### 2.1 Retool

- **一句话**：内部工具行业标杆，面向"会写点 JS 的开发者"，SaaS + 自托管。
- **架构核心**：
  - 应用 = 一份 **JSON app definition**（组件树 + 属性 + queries），浏览器端运行时把 JSON 渲染成组件树；
  - `{{ }}` 模板表达式 + **依赖图求值**实现跨组件响应式数据流；
  - 数据层抽象为 "Resource + Query"，SQL 在服务端执行、密钥不下发浏览器；前端 JS 在沙箱（V8 isolate）中执行。
- **最值得学**：**依赖图驱动的绑定求值**——UI 组件、查询、事件共用同一套表达式引擎，用户改一个输入，整条数据链自动重算。数据流编程被它以最轻的方式落地。

### 2.2 Appsmith（开源，最推荐逐行读的参考实现）

- **一句话**：开源（Apache-2.0）内部工具平台，源码全开放。
- **架构核心**：
  - 前端 React + Redux；页面由 **Widget DSL（JSON）** 作为唯一事实源；Canvas 层用 WidgetFactory 按类型把 DSL 渲染成组件树；
  - **evaluation engine** 解析 `{{ }}` 绑定、建依赖图、沙箱求值后写回状态触发重渲；
  - **渲染层与求值层彻底分离**——这是它的架构精髓。
- **最值得学**：两层的边界。"Canvas 只负责渲染、Evaluation 只负责求值"，教学级拆解的最佳范本。

### 2.3 Budibase / ToolJet

- Budibase：开源 AGPL，**自带数据库 + 自动 CRUD**——"建表后自动生成表单/列表/CRUD 页面"，展示"数据模型作为底层 schema、UI 是它的视图投影"这条极简路线。
- ToolJet：开源 AGPL，React 前端 + Node 后端 + Postgres 存储 + 50+ 数据源连接器，事件驱动逻辑编排（widget 事件 → 触发 query/导航/JS 动作），内置 git 版本化。它的 **显式事件-动作编排模型**与 amis 的 onEvent 一脉相承。

## 3. 企业级 aPaaS：Mendix / OutSystems / Power Apps

### 3.1 Mendix（西门子）

- 领域模型 + **Microflow（服务端逻辑，编译为 Java 执行）/ Nanoflow（客户端逻辑，编译为 JS）**两套可视化逻辑语言；
- Runtime 解释执行模型；React 客户端 + PWA/离线。
- **最值得学**：**逻辑也分成本可视化语言**——回答了"复杂业务逻辑如何在低代码里表达"。

### 3.2 OutSystems —— codegen 路线的样板

- Service Studio 可视化建模；一键 Publish 时编译器把模型编译成真实的 .NET/C#（服务端）+ JS/HTML/CSS（前端）+ SQL（数据库结构），部署到标准 Web 服务器。
- **最值得学**："模型即源码、可编译可审计"，是"低代码要过合规/可进既有 DevOps"这类诉求的标准答案。

### 3.3 Microsoft Power Apps

- Canvas 应用是 **JSON 文档**，schema 驱动运行时渲染；
- 核心是开放公式语言 **Power Fx**——Excel 风格、声明式、函数式，**组件每个属性都是一个可重算的公式**，依赖追踪自动重算（数据流而非事件流）；
- Model-driven 应用是另一套体系：纯元数据驱动、自动生成界面。
- **最值得学**：声明式属性公式引擎，"每个属性都是公式"的可测试、可复用思想。

---

## 4. 搭建框架类：lowcode-engine / amis（我们的双标杆）

这两个是我们要**参照写出我们自己平台**的对象，原理详见 `02-core-principles.md`，这里先给定位：

- **lowcode-engine（阿里）**：不直接提供成品页面，而是提供"**造低代码平台的引擎**"——协议、编辑器、渲染器、物料体系四件套做成可插拔能力。它的物科协议"一份 meta 驱动四处"是我们整个架构的支柱。
- **amis（百度）**：不做拖拽搭建器，做"**JSON 直接渲染成页面**"的低代码前端框架（配合 amis-editor 拖拽生成 JSON）。它的**数据链 + onEvent 动作链 + amis-formula 表达式**是我们"数据绑定/事件动作"两个子系统的直接参考。
- **tmagic-editor（腾讯）**：编辑器只产出 DSL、运行时（page/playground 双入口）共用同一份组件/数据源代码渲染——"单一 DSL 服务线上与画布"的示范。

---

## 5. 其他几类（定位对比，不深究）

- **表单流程 SaaS（简道云/明道云/氚云/轻流）**：技术共性是 运行时渲染 + 服务端元数据（表单定义 JSON + 流程定义）+ 多租户，差异化全在业务模型层（公式、审批流、报表、权限）。前端引擎实力弱于 amis/lowcode-engine。
- **云厂商 PaaS（宜搭/微搭/魔笔/爱速搭/CodeWave）**：宜搭"元数据驱动，一模型多渲染器（表单/流程/页面/报表）"；微搭绑定微信生态 + Serverless；魔笔强集成阿里云基础设施；爱速搭是 amis 产品化；CodeWave 走"可视化 DSL + 源码导出"双模。**火山引擎 veImageX 不是低代码平台**（是图片/视频处理服务），注意甄别。

## 6. 三条贯穿一切的原理性结论

### 6.1 运行时渲染 JSON vs 代码生成（codegen）

| | 运行时渲染（schema） | 代码生成（codegen） |
|---|---|---|
| 代表 | Retool、Appsmith、Bubble、Power Apps Canvas、**国内绝大多数** | OutSystems（最典型） |
| 优点 | 修改即生效、免构建发版；套路天然是数据（存储/版本化/热更新）；编辑态=运行态（WYSIWYG） | 产出标准技术栈产物，性能可优化，可进既有流水线与安全审计 |
| 缺点 | 解释器运行时开销、复杂页面性能受限、调试依赖平台 | 模型与代码双轨一致性成本、需要一个编译集群、大改成本高 |
| 趋势 | **两者在收敛**（出码仅作"不锁定"兜底，默认主链路仍是运行时） | |

国内主流走运行时渲染路线的 6 条理由：①反馈闭环快（改 JSON 即生效）②编辑态与运行态同构（预览=真实渲染）③SaaS 多租户天然契合（每个租户就是一组元数据）④中后台场景组件富、逻辑简，JSON 解释开销可忽略 ⑤出码多目标成本高（React/Vue/小程序 N 套生成器）⑥版本管理直接变成 schema diff。
> **我们的选择**：运行时渲染为主（M1 起），出码作为 M9 的第二通道——正好把两条路线都教学一遍。

### 6.2 布局系统：绝不用绝对定位

- **绝对定位画布**：类 Figma 自由画布，编辑直觉最好，**但不响应式、不可维护**——只适合设计稿语义。
- **流式 flex / 行-列容器**：内容自适应、天然响应式、实现最简单。**内部工具四件套 + Bubble 的默认**，因为产物是"真实可运行的 Web 应用"。
- **grid 栅格**：12 栏 + 可嵌套行/单元格（react-page 即此）。

> **我们的选择**：组件「堆叠 + 容器嵌套」的 flex 流式布局（每个容器就是一个 flex 列表），不引入栅格系统（文档中说明取舍）。

### 6.3 craft.js 范式：把"拖拽"降维成"树的纯函数操作"

页面编辑器的事实标准范式（craft.js / react-page）：

1. 编辑器维护一棵**扁平化的节点树**（`nodeId → { type, props, childrenIds, parentId }`，常归一化为 map）；
2. 一张 `type → 组件` 的 **resolver** 表完成映射；
3. 渲染 = 树遍历；**编辑态套一层 overlay（选中框/拖拽手柄），导出态只是干净渲染**（同一棵树，两套壳）；
4. 拖拽本身**永不直接改 DOM**，只把它翻译成树的 insert/move/remove 操作 → 不可变 state 更新 → 整树重渲。

> **我们的选择**：完全采纳这个范式。渲染引擎（SchemaNode）+ 编辑器 wrapper（CanvasNode）分离，是 M1/M3 的架构骨架。

---

## 7. 一句话总结

> 学低代码，学的是三个东西：**①用一份 schema 同时驱动 渲染/编辑/物料/出码 的声明式体系（lowcode-engine 的核心）；②数据链 + 表达式 + 动作链的表达力（amis 的核心）；③把"拖拽""渲染"等一切交互都降维成对一棵树的纯函数操作（craft.js 的核心）。** 这三条贯穿我们后面全部实现。
